# v1.1.1 三端发布

日期：2026-11-13。版本统一为 `1.1.1`，Android `versionCode=10101`，包名 `local.survival.apocalypse`。

## 下载与安装

所有文件均在 [v1.1.1 发布页](https://github.com/yuchen0x1/Doomsday-Survival-Guide/releases/tag/v1.1.1)。

| 平台        | 文件 / 入口                                                                                                | 使用方法                                                                                               |
| ----------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Web/PWA     | [在线访问](https://yuchen0x1.github.io/Doomsday-Survival-Guide/) / `apocalypse-survival-web-v1.1.1.tar.gz` | 浏览器可安装为 PWA。压缩包是静态网站，解压后用 HTTPS 或 localhost 托管，配置 SPA 回退到 index.html。   |
| Windows x64 | `apocalypse-survival-windows-x64-v1.1.1-setup.exe`                                                         | 运行安装程序。安装包包含 WebView2 离线安装组件。未进行 Authenticode 代码签名，系统可能提示发布者未知。 |
| Android     | `apocalypse-survival-android-v1.1.1.apk`                                                                   | 下载到手机后打开，按系统提示允许该来源安装。使用固定发布证书签名。                                     |

`SHA256SUMS` 覆盖三个包。下载到同一目录后，Linux/macOS 使用 `sha256sum -c SHA256SUMS`（macOS 也可 `shasum -a 256 -c SHA256SUMS`）；Windows 使用 `Get-FileHash -Algorithm SHA256 <文件>` 对照。校验和不替代 Windows 发布者身份签名。

三端的个人数据各自保存在本机。通过导出 / 恢复版本 1 JSON 备份可手动迁移，不会自动跨设备同步。升级前先备份，用同平台新包覆盖安装，避免卸载导致本地数据丢失。原生端尚未实现自动下载与安装更新；Web/PWA 保留确认后更新的机制。

## 构建与版本约束

- `scripts/verify-release-versions.cjs` 校验 Web、桌面、移动、Tauri、Cargo 与 Android 版本一致；发布标签必须匹配根版本。
- `.github/workflows/release-all.yml` 分别构建 Web、Windows、Android；三者成功后汇总工件并生成统一校验文件。标签触发构建；手动运行并启用 `publish_release` 才自动创建 Release。也可下载汇总工件，验收后使用 GitHub CLI 发布。
- `.github/workflows/release-web.yml` 仅保留手动 Web 构建入口；正常发布使用三端流程。
- Windows：`pnpm --filter @apocalypse/desktop build`，需要 Rust / MSVC。构建脚本关闭 PWA 注册并固定根路径，资源嵌入 Tauri 安装包。
- Android：`node scripts/build-native-web.cjs` → `pnpm --filter @apocalypse/mobile exec cap sync android` → `bash gradlew --no-daemon assembleRelease`。使用 JDK 21、Gradle 8.11.1、Android SDK 34。Windows 若路径包含中文，可用临时 ASCII 盘符映射到当前项目后构建。
- APK 通过 `apksigner` 签名并验证，Actions 使用 `ANDROID_KEYSTORE_BASE64`、`ANDROID_KEYSTORE_PASSWORD`、`ANDROID_KEY_ALIAS`。私钥和密码不进入 Git、工件或发布附件。
- 发布证书 SHA-256：`c842c487f8349c8e42ec13b8f1c08c8954f18199e10afb5312ce21db0a013449`。后续 APK 必须沿用此证书才能覆盖更新。

## 发布前暴露面审计

### 1. 总览

对本地 APK 与已安装的 Windows EXE 运行静态扫描，并检查签名、归档内容和实际运行。扫描器原始评分为 Android 98/B、Windows 69/C，评分是启发式排序，不是安全认证；下方对误报作人工复核。

### 2. 发现清单

| 编号            | 级别           | 证据及结论                                                                                                                                        |
| --------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| PE-SIGN         | 高             | Windows EXE 和安装程序的 Authenticode 状态为 NotSigned，发布者身份认证未完成。                                                                    |
| PE-PDB          | 中（降为信息） | PE 中只含 `apocalypse_desktop.pdb` 文件名，无开发机绝对路径，未随包发布 PDB。                                                                     |
| PE-CFG          | 低             | 本次 Windows EXE 未声明 Control Flow Guard；现状记录，未声称已启用。                                                                              |
| APK-ALLOWBACKUP | 低             | 沿用 Android 工程的 `allowBackup=true`；系统级备份受 Android 版本及用户设置影响。                                                                 |
| LEAK-INTRANET   | 误报           | 扫描到开发配置 `http://localhost:5173`，它是 Vite 开发地址，不是内部服务器或凭证。实际安装程序从 `tauri.localhost` 加载嵌入资源，已断网刷新验证。 |

### 3. 证据与处理

Android `apksigner verify --verbose --print-certs` 验证 v1/v2/v3 签名，`aapt dump badging` 确认版本与无 debuggable。v1 检查对部分 META-INF 元数据产生警告；v2/v3 整包签名仍验证通过。客户端资源未附带 `.map`、`.env`、签名私钥或密码。Windows 使用 release 优化和 strip；原生写文件只接受系统选择的目标，不向 WebView 暴露任意路径写入命令。

### 4. 客户端无法解决的问题

项目开源，内置知识、JS 和 Android DEX 都可读取；不把混淆当作保密措施。没有把付费授权或长期服务端密钥放入客户端。Windows SHA-256 文件校验无法替代可信代码签名；未来自动更新还需要独立的签名清单与安装验证。

### 5. 后续顺序

P0：维持私钥与密码只在本机受保护文件和 Actions Secrets 中；P1：有可用发布者证书后接入 Windows Authenticode；P2：独立评估 CFG、系统备份策略与原生工具链升级。当前没有签名证书，未伪造 Windows 签名状态。
